# Operations guide

English | [简体中文](operations.zh-CN.md) · [Project home](../README.md) · [Security](security.md) · [Configuration](configuration.md)

Use this guide to install, verify, and maintain a fresh VPS. The installer does not migrate an existing 3x-ui or Nginx deployment. An interrupted installation of this version can resume using its saved state.

## Deploy a fresh VPS

### 1. Prepare the server and configuration

Requirements: Ubuntu 22.04+ or Debian 12+, systemd, Python 3.10+, amd64 or arm64, and a static public IPv4 address. Have working SSH access and sudo privileges ready.

In the local project directory, create a configuration only if one does not exist. Edit an existing `config.json` without replacing its credentials:

~~~bash
test -f config.json || cp config.example.json config.json
chmod 600 config.json
nano config.json
bash ./install-3x-ui.sh --config ./config.json --validate-config
~~~

With the defaults—Direct routing, an SSH-only panel, and unlimited traffic—only `SERVER_IP` is required. ISP modes also require upstream credentials; a public HTTPS panel requires a domain. See [Configuration](configuration.md) for fields and examples.

`--validate-config` checks local syntax and configuration logic without sudo or network access. Passing does not establish that DNS, the upstream proxy, or public connectivity works.

### 2. Set up DNS and firewalls

When using a domain, point the `SUB_DOMAIN` A record directly to `SERVER_IP`, disable CDN proxying for that record, and wait for public resolvers to agree. Without a domain, subscriptions use an HTTPS certificate for the public IP and the panel uses an SSH tunnel.

Check both the cloud firewall and the host firewall. The script prints the required ports; it does not change firewalls or SSH settings.

| Default TCP port | Purpose | Public rule |
| --- | --- | --- |
| Actual SSH port, commonly 22 | Login, upload, SSH tunnel | Preserve management access |
| 80 | Certificate issuance and renewal | Keep reachable |
| 443 | Shared Direct / ISP node inbound | Allow |
| 2096 | Nginx HTTPS subscription gateway | Allow |
| 7777 | Public HTTPS panel | Allow only with `PANEL_HTTPS=true`; restrict management source IPs where possible |
| 12096 | Local subscription backend | Do not expose; listen only on `127.0.0.1` |

If ports change, follow the configuration validator's output. The default SSH-only panel does not need public port 7777. Direct and ISP share `NODE_PORT`; there is no separate ISP inbound port.

### 3. Upload and install

Run locally, replacing the SSH username and VPS IP. Upload the script version you intend to test or deploy:

~~~bash
scp ./install-3x-ui.sh ./config.json ubuntu@YOUR_VPS_IP:~/
ssh ubuntu@YOUR_VPS_IP
~~~

Run the preflight on the VPS:

~~~bash
chmod 600 ~/config.json
sudo bash ~/install-3x-ui.sh --config ~/config.json --check
~~~

After it passes, install:

~~~bash
sudo bash ~/install-3x-ui.sh --config ~/config.json --install
~~~

`--check` checks the system, port occupancy, ISP, DNS, REALITY target, and certificate prerequisites without installing software or changing services. `--install` installs components, obtains a certificate, configures the node and subscription gateway, and runs server-side checks.

Subscriptions use the dedicated `3x-ui-subscription.service`. The distribution's default `nginx.service` is deliberately masked, leaving port 80 available to Certbot's standalone validation service.

### 4. Open the panel and import subscriptions

Installation prints credentials, the complete panel URL, Mihomo / Shadowrocket subscriptions, and VLESS links. Display them again on the VPS with:

~~~bash
sudo bash ~/install-3x-ui.sh --show
~~~

The output is saved in `/var/lib/3x-ui-bootstrap/result.txt`, readable only by root. Keep the installation output and complete subscription URLs private.

For the default SSH-only panel, open another local terminal and establish a tunnel. This command uses the default panel port:

~~~bash
ssh -N -o ExitOnForwardFailure=yes \
  -L 127.0.0.1:17777:127.0.0.1:7777 ubuntu@YOUR_VPS_IP
~~~

Keep the tunnel running and open the complete `http://127.0.0.1:17777/` URL, including its random path, from the installation output. For a public HTTPS panel, use the printed HTTPS URL directly.

Import the subscriptions generated by this installation into the corresponding clients. Dual mode provides `<name>-Direct` and `<name>-ISP`: both connect to the same VPS port with different UUIDs and subscription IDs. Opening a valid subscription in a browser downloads data; it does not display a subscription information page.

## Verify the deployment

On the VPS, check services and listeners:

~~~bash
sudo systemctl status x-ui 3x-ui-subscription --no-pager
sudo ss -lntp | grep -E ':(2096|12096)\b'
~~~

With default ports, Nginx should listen on `0.0.0.0:2096` and x-ui only on `127.0.0.1:12096`. Substitute configured ports when necessary.

Then verify from real clients:

1. Subscription updates succeed and quota information refreshes.
2. Browse through Direct and ISP separately. Direct should exit through the VPS IP; ISP should use the provider's exit.
3. From your computer, request `/`, `/assets/`, and `/sub/assets/` on the subscription endpoint. They should return 404; a complete valid subscription URL should download successfully.

Node connections use 443 by default; subscription updates use 2096. Test both. Server-side checks and a successful TCP connection do not replace real VLESS authentication and public client acceptance. A desktop TUN can intercept probes, so check the actual network path.

On 2026-11-01, a user reported the new deployment working, and external IPv4 exposure checks were completed. See [Security](security.md) for their scope. Client versions were not recorded for this deployment, so this is not a compatibility claim for all versions.

## Routine maintenance

Run these commands on the VPS. The configuration file contains proposed settings; editing it alone does not change running services.

| Action | Command |
| --- | --- |
| Display credentials, panel and subscription URLs | `sudo bash ~/install-3x-ui.sh --show` |
| Read native monthly client usage | `sudo bash ~/install-3x-ui.sh --traffic-status` |
| Diagnose REALITY using a temporary copy | `sudo bash ~/install-3x-ui.sh --diagnose` |
| Apply domain, HTTPS panel, and email settings | `sudo bash ~/install-3x-ui.sh --config ~/config.json --configure-domain` |
| Apply names, mode, ISP, and quota settings | `sudo bash ~/install-3x-ui.sh --config ~/config.json --configure-nodes` |
| Change monthly quotas while preserving the original reset day | `sudo bash ~/install-3x-ui.sh --config ~/config.json --configure-traffic` |
| Repair the deployed REALITY target | `sudo bash ~/install-3x-ui.sh --repair-reality-target` |

`--show`, `--traffic-status`, `--diagnose`, and `--repair-reality-target` use saved server data and do not require a configuration file. Each `--configure-*` command updates a specific group of fields; see [Configuration](configuration.md). Service changes can briefly interrupt connections. Follow the resulting instructions to update clients.

`--diagnose` uses temporary loopback copies without changing existing nodes or services; it does not reproduce the production ISP outbound. `--repair-reality-target` changes the production deployment and is intended for a diagnosed target problem.

After manually changing ISP credentials in the panel, update the private configuration before running `--configure-nodes`. Keep managed subscription IDs, paths, and listeners under script control so they remain consistent with the Nginx allowlist.

## Inspect services and certificate renewal

On the VPS, start with service state, listeners, and logs:

~~~bash
sudo systemctl status x-ui 3x-ui-subscription --no-pager
sudo ss -lntp
sudo ufw status verbose
sudo journalctl -u x-ui -n 80 --no-pager
sudo journalctl -u 3x-ui-subscription -n 80 --no-pager
~~~

Also inspect the cloud firewall. `ufw inactive` only means UFW is not enabled; it does not establish that the cloud firewall allows traffic. Redact logs before sharing them; see [Security](security.md).

Check Nginx and certificate renewal with:

~~~bash
sudo /usr/sbin/nginx -t -c /var/lib/3x-ui-bootstrap/nginx.conf
sudo systemctl status 3x-ui-cert-renew.timer --no-pager
sudo journalctl -u 3x-ui-cert-renew.service -n 80 --no-pager
~~~

Use `-c` to select the managed configuration; the default Nginx configuration is not the subscription gateway. Renewal reloads or starts the gateway and also restarts x-ui when the public HTTPS panel is enabled.

Keep port 80's public rules available for certificate validation. A persistent listener on port 80 is not required between validations. The subscription backend uses local HTTP and does not need a separate public certificate. Do not expose 12096 to troubleshoot a subscription failure.

## Troubleshooting

### Configuration validation fails

Run `--validate-config` again. JSON must not contain comments; ports must be numbers, Boolean values must be `true` / `false`, and the file must have mode 600. This checks format and logic only. Use `--check` on the VPS for DNS, ISP, and system prerequisites.

### The domain still resolves to the previous IP

Check the authoritative A record and public resolver answers, disable CDN proxying for that record, and wait for TTL expiry and propagation. Clearing the VPS's local cache cannot force public recursive resolvers to refresh early.

### The panel or subscription is unreachable

Check the complete URL's scheme, port, random path, and subscription ID. The SSH panel needs a running tunnel; a public HTTPS panel needs its port allowed. If subscription updates fail, inspect the gateway on 2096 and DNS separately.

### The subscription root or assets return 404

This is expected. Only complete valid download URLs are accepted, without a homepage, static assets, invalid IDs, or additional query parameters. Update the subscription in the client; a visible homepage is not a health check.

### Only one Direct / ISP route works

Check that client's quota, enabled state, UUID, and routing. Both routes share one VLESS + REALITY inbound. Rules must match both the inbound tag and the client email (`user`), routing to `direct` or `bootstrap-isp`. Matching only the shared inbound tag cannot distinguish the two clients.

ISP UDP is blocked, and upstream failure does not fall back to Direct. Quotas are metered independently; exhausting one does not automatically consume the other's allowance. Renaming a client does not change its exit.

### The ISP outbound test passes, but clients cannot connect

Check the upstream proxy, production inbound authentication and forwarding, and the client's public connection to the VPS separately. Compare Wi-Fi and cellular access; inspect packets for the affected connection if necessary. After changing `bootstrap-isp` in the panel, preserve the inbound tag, client email, and user routing, then save and apply. Do not start by reinstalling.

### Shadowrocket cannot connect

The historical version-specific result is **Shadowrocket 2.2.92 (3345) + Xray-core 26.6.27**, from the previous dual-inbound deployment. The current fresh deployment was reported working, but its client versions were not recorded, so it does not extend that version matrix.

Check that the core remains at the pinned 26.6.27 version. Verify the UUID, Vision flow, REALITY public key, SNI, short ID, address, and port. After changing either core or client, retest import, browsing, exit IP, and quota refresh.

### Installation or a configuration change was interrupted

Keep `/var/lib/3x-ui-bootstrap`, the database, and private logs. Fix the cause and retry the same command with the same configuration. Resume interrupted domain, node, or target changes with `--configure-domain`, `--configure-nodes`, or `--repair-reality-target` respectively. Do not delete state and reinstall.

Resumption applies only to deployments managed by this version. If files from another version or a manual installation are detected, deploy on a fresh VPS instead of migrating the old host.
